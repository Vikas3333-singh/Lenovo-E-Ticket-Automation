Why it exists

Creating tickets was typingFaulty motherboards and power faults need a Lenovo warranty claim. Each claim meant 15+ fields by hand: serial number, issue, contact, dispatch address. Around 30 or more tickets a month.
Tracking tickets was logging inEvery day, someone opened the portal to see whether the technician had visited and whether the part was changed. A wrong dispatch address sent the technician to the wrong place.
Before: 15+ fields by hand daily portal loginAfter: one command to create, one command to sync

What happens on each run

  1. Read the trackerSerial number, issue, and dispatch location come from each Excel row.
  2. Log in to the portalSelenium controls a real browser, clicking and typing like a person would.
  3. Fill the form and submitEvery field is filled from the row, then the ticket is submitted.
  4. Write the Case ID backLenovo returns an ID such as #4010892211. The script captures it into the same row.
  5. Sync status the next dayEach active ticket is opened, its status read, and the sheet updated.

Three things it handles

Bulk ingestion

The whole list runs in one go instead of one ticket at a time.

Dynamic routing

Users at home or at a branch get an alternate dispatch address, read from each row so nobody edits the form. Try it above: those rows and their address fields turn amber.

Next-day sync

Status for every active ticket lands in Excel with no manual login.

Design choices

Excel remains familiar

Excel can remain the intake and export format, while a central database becomes the permanent record for assets, tickets, Case IDs and status history.

It drives the real portal

Selenium operates the portal’s own pages, clicking and typing the way a person would, so nothing on the portal side has to change.

What it will take to run this reliably at company scale

These are the controls I recommend adding before a wider rollout. They are implementation commitments, not claims that every control is already present in the current demo.

1. Stop duplicate tickets

Before submitting, the system will check the database for an existing open ticket using the asset serial number, issue category and a defined time window. Each request will also receive a unique idempotency key. If the same row is processed again, TicketForge will reuse the existing Case ID instead of creating another ticket. An operator can override the check with a recorded reason when a genuinely new case is required.

2. Recover safely from portal errors

Portal actions will have explicit timeouts, page and confirmation checks, and limited retries with increasing wait times. If submission times out after the portal may have accepted it, the job will first search for the resulting case before trying again. Unresolved jobs will move to an exception queue for review; the system will not blindly resubmit.

3. Keep credentials out of files and code

Portal credentials will be stored in an approved secrets vault or enterprise credential manager, not in Excel, source code or configuration files. Access will be restricted to the automation service account, secrets will be masked in logs, and rotation will follow company IT policy. MFA and portal terms will be respected; no attempt will be made to bypass security controls.

4. Use a proper database

PostgreSQL will hold the permanent records for assets, requests, tickets, Case IDs, status changes and job results. Excel will be used for controlled import/export only. Unique constraints and transactions will protect records from accidental duplication or partial updates, with scheduled backups and a tested restore process.

5. Keep an audit trail

Every run will record who or what started it, the asset reference, time, action, result, portal Case ID, retry count and any exception. Logs will be searchable and access-controlled, with sensitive fields and credentials excluded. Changes to ticket data and manual overrides will retain the user, timestamp and reason.

6. Prove it in an authorized test environment

The pilot will use a Lenovo-approved test account or designated low-risk test assets, with permission from the portal owner. We will demonstrate the complete flow: read an approved asset, check for duplicates, submit the request, capture the actual Case ID, store it in the database, and retrieve the real status. The demo will show timestamps, run logs and the resulting portal record. Sample data on this webpage is only a UI walkthrough, not proof of a live portal transaction.

How I would deliver the changes

  1. FoundationConfirm the approved portal workflow and test access; define the ticket matching rules; create the database schema and service account.
  2. Reliability controlsImplement duplicate checks, safe retry and exception handling, secrets-vault integration, structured logs and audit history.
  3. End-to-end pilotRun a small, agreed test batch in the authorized environment. Verify each Case ID and status against the portal and record the results.
  4. Production readiness reviewReview access permissions, backup and recovery, monitoring, failure procedures and operational ownership with IT and the portal owner.

Acceptance criteria: no duplicate submission during repeat-run tests; no blind retry after an uncertain submission; credentials absent from workbook, source and logs; every action traceable; and a successful, independently verified end-to-end test in the authorized environment.

Limitations

  • It depends on the portal’s page layout. If Lenovo changes the UI, the selectors need updating.
  • It needs your own authorized portal account.
