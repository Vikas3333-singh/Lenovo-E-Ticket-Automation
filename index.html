01 — The problem

The repetitive work

Every faulty motherboard or power fault needs a Lenovo warranty claim. The form has more than 15 fields, and the team files roughly 30 claims a month. Someone also has to check the portal each day to see whether a technician has visited or a part has been replaced.

Creating claims was manual data entry

Each claim required a serial number, issue, contact details and dispatch address. A mistyped postcode could delay the repair.

Status checks required a daily login

If nobody checked the portal, the tracker went out of date.

Before: 15+ fields typed by hand · a daily portal login → ✓ After: one command to submit claims, one to update status
02 — How it runs

What the two scripts do

The submission script handles rows one at a time. The status script only reads existing tickets. The steps below light up while the demo above is running.

  1. Read the Excel rowThe script reads the serial number, issue and dispatch location from the tracker.
  2. Open the portalSelenium signs in with the service account and opens the warranty claim form.
  3. Submit the claimIt fills the form from the row. If the user is at a branch or at home, it uses the alternate dispatch address stored in that row.
  4. Save the Case IDAfter Lenovo accepts the claim, the script reads the Case ID and writes it to the same row.
  5. Sync status the next dayA second script opens each active Case ID, reads its status and updates the sheet. It does not submit anything.
03 — Functions

Main functions

Batch submission

The script processes the whole tracker in one run and logs each row.

Dispatch routing

The row decides whether the claim uses the registered office or an alternate address. The demo marks those fields in amber.

Status updates

The status script writes technician and repair status back to Excel without a manual portal login.

04 — Design

Design decisions

Excel remains the input format

Teams can keep using Excel for intake and export. PostgreSQL stores the permanent record of assets, tickets, Case IDs and status history.

Selenium uses the existing portal

The automation clicks and types in the same pages a person uses. Lenovo does not need to provide an API.

05 — Scale

Controls for a wider rollout

The demo shows the workflow. A production rollout needs the following controls. Some are not implemented in the demo.

1. Prevent duplicate claims
Before submission, the script checks PostgreSQL for an open ticket with the same serial number and issue within a set time window. Each request has an idempotency key. If a row is processed twice, the script reuses the existing Case ID. An operator can override the check and must record a reason.
2. Handle portal errors
Each portal action has a timeout, a page check and a confirmation check. Retries are limited and use increasing delays. If a submission times out after the portal may have accepted it, the script searches for the case before retrying. Unresolved jobs go to an exception queue.
3. Protect credentials
Credentials live in a secrets vault or enterprise credential manager. They are not stored in Excel, source code or config files. Only the automation service account can read them. Logs mask secrets. The workflow respects MFA and portal terms.
4. Use a database
PostgreSQL stores assets, requests, tickets, Case IDs, status changes and job results. Excel is for import and export. Constraints and transactions prevent duplicate or partial records. Backups are scheduled and restores are tested.
5. Keep an audit trail
Each run records the initiator, asset, timestamp, action, result, Case ID, retry count and exceptions. Logs exclude secrets and sensitive fields. Manual overrides record the user, time and reason.
6. Test in an authorized environment
The pilot uses a Lenovo-approved test account or low-risk test assets, with permission from the portal owner. The test covers duplicate check, submission, Case ID capture, database write and status retrieval. The sample data on this page is a UI walkthrough. It is not evidence of a live portal transaction.
06 — Delivery

Rollout plan

The work has four stages. Each stage ends with a reviewable result.

  1. FoundationConfirm the approved portal workflow and test access. Define ticket-matching rules. Create the database schema and service account.
  2. ReliabilityAdd duplicate checks, safe retries, exception handling, secrets-vault integration, structured logs and audit history.
  3. PilotRun an agreed test batch in the authorized environment. Check each Case ID and status against the portal and record the results.
  4. Readiness reviewReview permissions, backup and recovery, monitoring, failure procedures and ownership with IT and the portal owner.

Acceptance criteria

  • A repeat run creates no duplicate claim.
  • The script does not retry a submission when the result is unknown.
  • Workbook, source code and logs contain no credentials.
  • Each action has a user or service account, timestamp and result.
  • An authorized end-to-end test passes and is independently checked.
07 — Limits

Limitations

  • The script depends on the portal's page layout. A UI change requires selector updates.
  • It needs an authorized portal account. It does not bypass login, MFA or access controls.
